# O-Cleaner 自定义数据格式规范（可导入 / 可由 AI 生成）

O-Cleaner 支持三类可迁移的自定义数据，打包成一个 JSON 文件（下称**自定义数据包**），
通过界面「自定义规则」面板 →「导入 / 导出自定义数据」读写，或直接调用本机 HTTP 接口：

| 接口 | 作用 |
|---|---|
| `GET  /__oc__/bundle/export` | 导出当前全部自定义项（导出文件本身就是标准样例） |
| `POST /__oc__/bundle/import` | 导入数据包；**逐项校验**，每一项被跳过的原因都会返回 |

> 资源包（packs）有自己独立的导入通道（界面「资源包」面板），不在这份数据包里；
> 其格式见 [packs/README.md](../packs/README.md)。

## 整体结构

```json
{
  "kind": "ocleaner-custom",
  "version": 1,
  "units":     [ { "label": "部 1080p 电影", "size": { "value": 2, "unit": "GB" },
                   "note": "常见流媒体画质", "category": "影音" } ],
  "overrides": { "pip-cache": { "what": "……", "keep_if": "……", "cleanable": false } },
  "rules":     [ { "name": "每周清缓存", "ids": ["uv-cache", "pip-cache"], "auto": false } ]
}
```

`kind` 必须是 `ocleaner-custom`，`version` 目前是 `1`；两个字段缺失或不符整包拒绝。
`units` / `overrides` / `rules` 三个小节都可以只给需要的部分，也可以全空
（那样导入就没有任何效果，接口会如实返回 0）。

## units —— 换算单位

把「累计释放量」换算成生活单位（多少张照片、几部电影）。

| 字段 | 必填 | 说明 |
|---|---|---|
| `label` | 是 | 展示名，如「部 1080p 电影」；**同名单位会被跳过**（不会重复导入） |
| `bytes_per_unit` | 二选一 | 一个单位等于多少字节（数字 > 0） |
| `size` | 二选一 | 更友好的写法：`{"value": 2, "unit": "GB"}`，unit 支持 B/KB/MB/GB/TB |
| `plural` | 否 | 复数/展示别名，缺省用 `label` |
| `note` | 否 | 估算依据，会显示在界面上，**建议写明**（如「按 320 kbps 约 8 MB/首」） |
| `category` | 否 | 分组名，缺省「自定义」 |
| `id` | 否 | 提供且与已有单位相同时更新那一项；缺省自动生成 |

## overrides —— 释义与结论覆盖

改写某个清理项的说明文字，或把「可清理」改成「不可清理」（反之亦然）。
优先级：**用户覆盖 > 资源包 > 内置知识库**。

- **键（ovkey）**：普通清理项用它的 `base_id`（如 `pip-cache`、`steam`），
  界面上卡片「编辑」弹窗保存的就是这个键；「自动发现」与自定义目录下的项
  没有稳定的 base_id，键是**归一化小写路径**（如 `d:\baidunetdiskdownload`）。
  最省事的获取方式：先在界面上改一条并导出，看导出文件里的键长什么样。
- 值是对象，四个文案字段任意组合、至少给一个，否则该项跳过：
  `what`（是什么）/ `rebuild`（能否重建）/ `impact`（删除影响）/ `keep_if`（建议保留），
  每段不超过 2000 字；
  `cleanable`：布尔值，可省略。
- 键不合法（空、超 200 字符、含路径分隔符）的项会被跳过并在报告中说明。
- **翻转 `cleanable` 不会改变风险等级**：高风险项即使被改成可清理，
  清理时仍按高风险处理（默认删进回收站）。

## rules —— 固定项勾选规则

一组预先勾选好的清理项集合，导入后出现在「自定义规则」面板，可一键套用。

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 规则名；**同名规则会更新**（以导入为准） |
| `ids` | 是 | 清理项 id 数组；**必须是当前真实存在的目标 id**，否则整条跳过 |
| `auto` | 否 | `true` = 套用时立即清理（默认 false） |
| `drive` | 否 | 适用于哪个盘，缺省 `C` |

`ids` 怎么取：`GET /__oc__/state?drive=C` 返回的每个目标都有 `id` 与 `base_id`
（盘符专属项的 id 带 `@盘符` 后缀）；或者从导出文件里现成的 rules 抄。
**导入校验用的正是同一份目标清单**，所以不存在"AI 编一个不存在的 id 混进来"的可能。

## 让 AI 帮你生成

两种用法：

1. **参照导出文件改**：界面点「导出自定义数据」，把导出的 JSON 发给任意 AI 助手，
   说「照这个格式帮我加几条……」，把 AI 返回的 JSON 再导入。
2. **从零生成**：把本页（整份规范）发给 AI，加上你的需求，例如：

   > 按下面这份格式规范，帮我生成一个 O-Cleaner 自定义数据包：
   > 加 3 个换算单位（微信聊天记录按 50 MB/年、……）、
   > 把 pip 缓存的「建议保留」说明改写得更谨慎、
   > 生成一条名为「深度开发清理」的规则。只输出 JSON。

   拿到 JSON 后导入即可。**导入接口就是验收器**：AI 编错字段、用了不存在的 id、
   写了超长文本，都会被逐项跳过并说明原因——把返回的 `*_skipped` 内容发给 AI
   修正再导，两三轮内就能全部收下。

## 导入的行为语义（写给实现者 / AI）

* 整包先验 `kind`/`version`，不符直接 400，**不会部分生效**；
* 三小节内部逐项独立校验：坏项跳过、好项照常收下，结果在返回值里逐条报告；
* 单位按 label 去重（重复跳过）、按 id 更新；规则按 name 更新（同名覆盖）；
* 覆盖按键 upsert；全部留空的覆盖条目等于删除该键的既有覆盖；
* 规则的 `ids` 校验发生在导入时——换了机器 / 换了盘符后旧规则的 id 可能失效，
  重新导入一次（或用界面重新勾选保存）即可修复；
* 所有写入走与界面相同的保存通道（原子写），导入失败不会留下半成品。
